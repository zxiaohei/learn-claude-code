# 智能体构建器

为任何领域构建 AI 智能体——客户服务、研究、运营、创意工作或专业业务流程。

## 核心理念

> **模型本身已经知道如何成为智能体。你的任务是不要妨碍它。**

智能体并不是什么复杂工程。它只是一个让模型能够采取行动的简单循环：

```
循环：
  模型看到：上下文 + 可用能力
  模型决定：行动或回应
  如果行动：执行相应能力，加入结果，继续循环
  如果回应：将结果返回给用户
```

**仅此而已。** 魔力不在代码里，而在模型中。你的代码只是提供了让模型发挥作用的机会。

## 三个要素

### 1. 能力（它能做什么？）

智能体可以执行的原子操作：搜索、读取、创建、发送、查询、修改。

**设计原则**：从 3～5 项能力开始。只有当智能体持续因为缺少某项能力而失败时，才增加更多能力。

### 2. 知识（它知道什么？）

按需注入的领域专业知识：政策、工作流、最佳实践、数据结构。

**设计原则**：让知识随时可用，而不是强制加载。在相关时加载，不要一开始就全部载入。

### 3. 上下文（发生过什么？）

对话历史——将多个行动串联成连贯行为的线索。

**设计原则**：上下文十分宝贵。隔离嘈杂的子任务，截断冗长的输出，保持内容清晰。

## 智能体设计思路

构建之前，先理解：

- **目的**：这个智能体应该完成什么？
- **领域**：它在哪个场景中运作？（客户服务、研究、运营、创意……）
- **能力**：哪 3～5 项操作必不可少？
- **知识**：它需要访问哪些专业知识？
- **信任**：哪些决策可以交给模型？

**关键要求**：信任模型。不要过度设计，也不要预先规定工作流。提供能力，让模型自行推理。

## 渐进式复杂度

从简单开始。只有实际使用表明确有需要时，才增加复杂度：

| 级别 | 添加内容 | 何时添加 |
|------|----------|----------|
| 基础 | 3～5 项能力 | 始终从这里开始 |
| 规划 | 进度跟踪 | 多步骤任务失去连贯性时 |
| 子智能体 | 隔离的子智能体 | 探索过程污染上下文时 |
| 技能 | 按需知识 | 需要领域专业知识时 |

**大多数智能体永远不需要超过第 2 级。**

## 领域示例

**业务**：CRM 查询、电子邮件、日历、审批
**研究**：数据库搜索、文档分析、引用
**运营**：监控、工单、通知、升级处理
**创意**：素材生成、编辑、协作、审阅

这一模式是通用的，变化的只有能力。

## 关键原则

1. **模型就是智能体**——代码只负责运行循环
2. **能力使行动成为可能**——它能做什么
3. **知识提供信息**——它知道如何做什么
4. **约束聚焦目标**——限制带来清晰度
5. **信任释放潜力**——让模型自行推理
6. **迭代揭示需求**——从最小方案开始，根据使用情况演进

## 反模式

| 模式 | 问题 | 解决方案 |
|------|------|----------|
| 过度设计 | 在产生需求之前引入复杂度 | 从简单开始 |
| 能力过多 | 使模型困惑 | 从 3～5 项开始 |
| 僵化工作流 | 无法适应变化 | 让模型决定 |
| 预先加载知识 | 上下文膨胀 | 按需加载 |
| 微观管理 | 削弱智能 | 信任模型 |

## 智能体思维方式

**从**：“怎样让系统执行 X？”
**转向**：“怎样让模型具备执行 X 的能力？”

**从**：“这个任务的工作流是什么？”
**转向**：“哪些能力有助于完成这个任务？”

最好的智能体代码几乎平淡无奇：简单的循环、清晰的能力、干净的上下文。魔力不在代码里。

**赋予模型能力和知识，相信它能找出其余部分。**
